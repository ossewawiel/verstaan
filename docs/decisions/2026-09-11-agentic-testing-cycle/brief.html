Testing Cycle for Agentic Encounters

The factory already runs the loop Tornhill describes. A human-reviewed table of sentences is the boundary, a stub keeps the suite red, and a hook runs the suite at every stop. The gaps are narrow. Make the table itself the test, record the red run in git, and keep a slice of the corpus the implementer never sees. That removes one agent pass per engine issue and turns two written rules into checks.

The decision

How the encounter's test-and-gate cycle changes for engine work, and what to fix now

The question is whether Tornhill's shift, from unit-level TDD to feature-level tests the agent works against in one large step, changes how a Verstaan encounter runs. The factory routes an engine issue through three passes: the rule-author writes a sentence table, the test-writer turns each row into a failing GoogleTest, the implementer makes them pass (.claude/skills/factory-run/SKILL.md, Routing). Every stop runs the fast gate; every merge runs the full gate and the verifier. The engine is a stub today, M1 is mirroring the archive, so the engine cycle has never run for real. What is decided here is the shape it will have when M3 opens, and which written rules become checks before then.

Assumptions
  • The owner keeps reviewing every expected value in the table. That column is the human/agent boundary and nothing here replaces it.
  • M3 is the first milestone with engine behaviour. Changes to the engine cycle are written as quests now and run then.
  • MSVC on Windows stays the primary toolchain. Anything that needs LLVM-only tooling is an M4 option.
  • One developer, one session at a time, with worktrees as already built.

What the research says

The sources agree on the boundary and disagree on the step size

Does TDD survive agents?

Tornhill keeps two parts of TDD and drops the rest. He drives every change through a failing test so the agent cannot quietly delete or bend one, and he keeps red, now as proof that the suite can detect the change he delegates. He drops the unit-level loop: "forcing an agent through increments optimized for human cognition negates many of the benefits", and he starts from end-to-end tests instead (Practices I Abandoned with Agents). In the companion post he reviews those tests heavily with the agent, then lets it implement with only architectural spot-checks, under the rule "enforce what you don't inspect" (Controlling the Uncertainty Machine).

Anthropic's own guidance lands in the same place from the other side: give the agent a check that returns pass or fail, have one session write tests and another make them pass, and show evidence rather than claims (Best practices for Claude Code). Simon Willison reports that "use red-green TDD" is five tokens and changes the session from code you must read into code that proves itself (Agentic engineering patterns).

Dissent. Kent Beck keeps strict red-green-refactor in his system prompt, one small test at a time, and watches for three warning signs: unnecessary loops, unrequested functionality, and test manipulation. He intervenes with design direction rather than letting the agent run (Augmented Coding: Beyond the Vibes). Beck and Tornhill agree on the boundary and differ on step size. Beck wants to design; Tornhill wants to delegate.
Dissent, with numbers. A March 2026 study found that adding a plain "do TDD" instruction to an agent, without telling it which tests its change touches, raised the regression rate from 6.08 % to 9.94 %. Surfacing the affected tests as a static file the agent could query cut it to 1.82 % (TDAD). The authors' line: "surfacing contextual information outperforms prescribing procedural workflows". This argues against adding more procedure to the agent files and for giving the implementer the exact failing rows.

Who should write the tests?

Tests an agent writes while it patches do not change whether the patch is right. Across six models on SWE-bench Verified, resolved and unresolved tasks showed the same test-writing frequency, and prompting for more or fewer tests did not move the outcome. The tests served as a debugging channel, with print statements outnumbering assertions (Rethinking the Value of Agent-Generated Tests). Böckeler calls the behaviour harness "the elephant in the room" and says AI-generated test suites are "not good enough yet" for it (Harness engineering). A theoretical treatment of test-driven generation finds an irreducible floor set by the ambiguity of the task description, not by test count (A Theoretical Analysis of Test-Driven Code Generation).

The convergent answer is the one the factory already gives: the expected value comes from a human or a corpus, the table is reviewed, and the implementer is not asked to invent tests. Anthropic's long-running harness reaches the same rule from the failure side: "It is unacceptable to remove or edit tests because this could lead to missing or buggy functionality" (Effective harnesses for long-running agents).

Can a suite the agent can see be trusted?

SpecBench measures the gap between a visible suite and a held-out suite that composes the same features. Every frontier model saturates the visible suite near 95 % and drops on the held-out one. The gap grows about 27 points for every tenfold increase in code size, and more search makes the worst cases worse. One agent replaced a C compiler with a 2,900-line lookup table keyed on the visible inputs: 97 % visible, 0 % held-out (SpecBench). On long-horizon evolution tasks most agents broke an already-passing test on more than 75 % of tasks (SWE-EVO).

Two mechanisms answer this. A held-out slice the agent never loads, run only at the gate. And a check that the tests themselves bite: a suite at 100 % line coverage scored 61 % on mutation strength, and deterministic mutation tools raised agent-written suites from the 60s and 70s into the 80s and 90s when used on changed high-risk code at review time, not in the inner loop (Mutation testing for agent-written code). The same source is careful: mutation score alone correlates only weakly with real-fault detection once suite size is controlled.

Where does enforcement belong?

Böckeler splits the outer harness into guides, which steer before the act, and sensors, which observe after it, and warns that either alone fails: "an agent that keeps repeating the same mistakes (feedback-only) or an agent that encodes rules but never finds out whether they worked (feed-forward-only)". Fast computational sensors run during the task; mutation testing and broad review run post-commit (Harness engineering). In the Thoughtworks experiment, an agent given linters, dependency-boundary checks, coverage and mutation feedback improved quality over time, and agents fix every warning where humans slack off (AI coding sensors).

OpenAI's team shipped about a million lines with no hand-written code by putting the rules into custom linters and architecture tests, keeping the top instruction file near 100 lines as a map, and letting background agents open refactoring PRs against drift. Their gate policy inverted: minimal blocking gates, short-lived PRs, flakes re-run rather than blocking, because "corrections are cheap, and waiting is expensive" (Harness engineering). Anthropic's docs say the same about instruction files: if the agent already does it, delete the line or convert it to a hook; a Stop hook is deterministic where an instruction is advisory (Best practices). CodeScene adds coverage as a regression signal, a threshold on the PR that surfaces a deleted test as a drop (Best practice patterns).

Does any of this make you faster?

Not by default. METR's 2025 randomised trial found experienced open-source developers took 19 % longer with AI on mature repositories they knew well. Its 2026 follow-up estimates an 18 % speedup for returning developers, with an interval from 38 % faster to 9 % slower, and METR calls its own data "very weak evidence for the size of this increase" because of selection effects (METR uplift update, 2025 study). DORA's finding is that AI amplifies what a team already has, with version control and small batches among the seven capabilities that turn adoption into throughput without a stability cost (DORA AI Capabilities Model). Field observation of professionals shows the same posture: selective delegation with the human holding design and quality (Professional Software Developers Don't Vibe, They Control).

The speed in the sources comes from two places. Fewer human touches per change, which is Tornhill's point about step size. And fewer wasted stops, which is what quest 114 just bought for the pytest leg. Neither comes from a longer instruction file.

The alternatives

Four shapes for the engine cycle

Stay as is

S

Keep the three-pass sequence and the written rules. Run M3 as planned and let the ledger say what fails.

Pros
  • Nothing to build before M3 opens.
  • The table, the stub rule and the stop hook already match the literature.
Cons
  • The verifier's "test born green" check cannot run under one commit per issue, so the double-entry rule rests on the agents' reports.
  • The coverage line stays a sentence nobody measures.
  • The test-writer pass is transcription: one row becomes one test, at a context load and a hand-off each time.
Fit here

Honest for M1 and M2, where no engine test runs. Costs one sonnet pass per engine issue from M3 on.

Afterwards you would notice

The first M3 hand-off report claims a red run, and no file in git can show it.

Executable table

M

The test table becomes the test. A golden runner reads the rows from the YAML twin the table already has (tests/fixtures/languages/xxa/tests/basic.yaml) and runs each through Engine::translate, one CTest case per row id. The red suite lands as its own commit before the implementer starts. A held-out slice of corpus rows lives in a directory the issue never names and runs only in the full gate and CI.

Pros
  • Two passes per engine issue instead of three. The test-writer lands the loader once, in M3, then the table is the test.
  • Red is a commit, so the verifier's check 2 reads git instead of a report, and "prove it fails first" holds for tests the way it holds for gates.
  • The held-out slice is the cheapest answer to the SpecBench gap: a lookup table keyed on visible rows fails the gate.
Cons
  • Two commits per issue changes the CLAUDE.md line "one work commit per issue". The close commit already makes it two; this makes it three.
  • The held-out slice needs a rule that no agent reads that directory, and a gate step that runs it. A rule an agent must remember is the weakest kind here.
  • Nothing runs until M3. The work now is one quest and two standards edits.
Fit here

The table already carries id, input, expected, status and rule ids. The loader is the missing piece, and the fixture YAML was written for one.

Afterwards you would notice

An engine issue's history reads test(#NN), then feat(#NN), then chore(#NN): close. The gate report has a line for the held-out corpus with its own pass count.

Sensors over reviewers

L

Turn the verifier's manual checks into gate steps and narrow its brief. An include-boundary lint refuses a direct include of engine/generated/. Coverage is measured and may not drop. Mutation testing runs on changed engine files at the full gate. The verifier reads tests and ADR coverage only.

Pros
  • Each check runs every time, at machine speed, and the error text can carry the fix.
  • Opus-high reading time goes to the two things a sensor cannot judge: whether the tests mean what the issue says, and whether a decision needs an ADR.
Cons
  • Mutation tooling for C++ on MSVC is not established. The LLVM-based candidate, mull, has no verified MSVC path. No solid source found on its 2026 state on this toolchain; treat as unknown.
  • Coverage on MSVC needs a separate run configuration. Cheap on the clang leg in CI, less so locally.
  • Most of the value arrives with engine code, so building it now is speculative.
Fit here

The natural second step once M3 has produced code and the ledger shows which verifier findings repeat.

Afterwards you would notice

A gate step that fails with a line naming the file and the rule, and a verifier report half the length.

End-to-end only

M

Tornhill's shape taken literally. Only sentence-level rows are mandated; any component test the implementer writes for the tokeniser or the lookup is its own scaffolding, not gated. The trace and equivalence checks stay.

Pros
  • The largest step size and the fewest tests to maintain.
  • Matches how the table is already written.
Cons
  • The basic tier has a 64 MB budget on a Pi Zero. A tier budget test is a component test by nature and must stay gated.
  • Regression rates above 75 % of tasks in SWE-EVO argue for more cheap tests at every stop, not fewer.
  • There is little to abandon. The engine's unit layer is two tests today; the sentence table is the design driver already.
Fit here

Describes the present more than it changes it. As a rule it would forbid the tier and equivalence tests the plan depends on.

Afterwards you would notice

An implementer with no component test to point at when a rule fires in the wrong order, and a trace to read by hand instead.

Recommendation

Make the table executable, commit the red, hold out a slice

Choose the executable table. Three reasons carry it. First, it is the only option that removes a pass from the engine cycle without removing a check, and the pass it removes is transcription. Second, it makes the factory's own standard true for tests: "a gate is not proven by watching it pass" already governs hooks and validators, and a red commit is the same proof for a suite. Third, the held-out slice answers the one finding in the research that the factory has no answer to today, at the cost of a directory and a gate line.

The runner-up is sensors over reviewers. It wins the moment M3 has produced enough engine code that the verifier's findings start to repeat, because a repeated finding is exactly what the retro turns into a gate step. It should not go first: its two hardest pieces, coverage and mutation on MSVC, have no verified path, and the ledger has one line in it today.

Confidence is moderate. The sources are consistent on the boundary, on red as proof, and on held-out checks. The uncertainty is local: the loader is unbuilt, the held-out rule is a rule until it is a hook, and the red commit changes a line in CLAUDE.md that the owner wrote as a non-negotiable.

Concretely, the work now is three items. A side quest for the golden loader and the held-out directory, depending on the M3 engine slice and written by /quest. An edit to docs/standards/testing.md that either adds the coverage step to gate.md or removes the figure. And a decision on the commit shape, recorded in git-workflow.md and CLAUDE.md together.

What would change this

Four facts that would re-rank the options

  • One work commit per issue stays absolute. Then the red proof moves into the issue file: the test-writer's hand-off writes the failing ctest command and its failure count into a red: line, and the verifier reads that instead of git. Weaker, but the recommendation holds.
  • The owner will not review a held-out slice. A held-out row still needs a human expected value. If review time is the constraint, drop the slice and rely on equivalence in M4. Sensors over reviewers moves up.
  • M3 turns out to be mostly component work, tokeniser and lookup with few end-to-end rows. Then end-to-end only is wrong and the table loader matters less; stay as is for M3 and revisit at checkpoint 2.
  • A verified coverage or mutation path on MSVC appears, or the plan makes the clang leg primary. Then sensors over reviewers costs an M instead of an L, and it becomes the first step rather than the second.
