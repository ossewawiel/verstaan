Section 1

What I think you're really asking

The console is the only surface Verstaan shows to its one developer. The factory writes STATE.md and issue files; the console reads them and paints them. The developer wants that surface to feel like operating a Battlestar-class capital ship playing an open-world RPG: a bridge, a DRADIS sweep, a mission log, a codex, a chart of known space and unmapped space. The mechanics of the project — issues, quests, retros, gates, factory runs — should present as encounters, patrols, jumps, and after-action reports. The console must inform first and entertain second, but the entertainment is not decoration; it is what keeps a solo multi-year project going.

In scope. A web/UI architecture decision under an existing React + Vite console with a pinned design system, backed by files on disk under docs/factory/. This is inside interrogation-time's remit.

  • A1The chassis (amber-on-hull, Orbitron, JetBrains Mono, snub-rectangle panels) is not up for renegotiation — quest 164 pinned it. This interrogation runs above the chassis.
  • A2Source of truth stays the files on disk: docs/factory/STATE.md, docs/factory/issues/*.md, docs/adr/*.md, git history. The console does not own state.
  • A3Audience is one developer, running a local service at 127.0.0.1:7864. Not a team dashboard. Not a public shrine.
  • A4The console runs offline; every asset ships with it. Revised on turn 5 (Q16): the console needs the network. Fonts and libraries still ship with it; GitHub and the model are live dependencies, and the bridge says so when either is out of reach.
  • A5The BSG name is a mood, not a licence. Colonial Fleet vernacular is used the way a genre paints itself, without Universal's logos, character names, or marks.
  • A6Added on turn 6 at the developer's request: the factory itself is part of what the console shows — the five agents under .claude/agents/, the four project skills and two commands, the eight hooks and the four hook events in settings.json, and the paths in playbook.md an encounter follows from quest to merge. "the skills and pipelines and paths to follow for development testing quest creation code reviewing etc … how the claude universe is put together for this project."

11 When the repo restructures, does the map follow by itself, or does someone move the tiles by hand? Answered
The problem, plainlyA map is a set of things with positions. The repo has things — folders, issue files, milestones — but nothing in it carries an x and a y. So the console must get positions from somewhere. There are two sources, and they fail in opposite ways. Hand-authored: a file such as docs/factory/map.yaml says "M3 Engine slice sits at (400, 120), 300 wide". A human reads it, the map looks like a place, and a returning developer remembers "engine is top-right". It rots: the day engine/ splits into engine/core and engine/rules, someone must edit the file or the map lies. Derived: a layout algorithm reads the tree and the issue files and computes positions on every load. It never rots. It also never looks like a place — a force layout re-shuffles when a node is added, so nothing stays top-right, and the visitor cannot build a memory of the terrain. Fog of war makes the choice sharper: an unbuilt milestone has no folder, so a derived layout has nothing to place. Only a hand-named region can stand for a place the project has not been to.
Why it mattersThis is not a detail. It decides whether the map is a chart the developer maintains (a data file, a validator, a gate) or a view the console computes (no file, no memory of terrain). The three shapes are laid out as map options M1–M3 below.
Eliminates"Never by hand" kills M1 and M3 and with them fog of war. "A small file is fine" keeps M3 alive, which is the only shape where fog of war and self-updating contents coexist.

L4 · Console as harnessL · Chosen target

The console server imports @anthropic-ai/claude-agent-sdk and calls query() with the quest's prompt, model, and effort from the issue's front matter. A canUseTool callback catches every AskUserQuestion, renders it in the console as orders awaiting, and returns the developer's answer as the tool result. The session id is written to the job record; after a console restart, resume: sessionId continues the same run. Streaming input lets the console send a follow-up mid-run.

Pros
  • Every documented piece exists: canUseTool for the question, resume for the restart, streaming input for a mid-run order.
  • The console sees the whole run — progress, cost, checkpoints — as one job, and the artifact-feedback scene from Q1 is native.
  • The SDK main loop holds an artifact watch, so a claude.ai brief still wakes the run on "Send to Claude".
Cons
  • The console becomes the only cockpit. A broken console blocks every quest until it is fixed from a terminal.
  • Credentials and billing under a server process are unverified (Q17).
  • The restart gate today kills running jobs; a quest job must be exempt and resumed, which is a change to restart.ts as well as kinds.ts.
Fit here Cleared on turn 5 (Q17). L1 and L2 stay alive as the staging steps so the flight deck works the week the map does not exist yet.
Afterwards Pressing Launch on quest 21 shows a session id under the tile, a token counter climbing, and after twenty minutes an amber card asking checkpoint 2's question with a text box under it.
Section 4

Recommendation

Build E on M1 with L4, in six quests, bridge first and harness last. Every room reads the files the factory already writes; the only new file is the atlas. Every action the console takes goes through the kind table in kinds.ts or the SDK call, never a shell string. After the six quests, a rebooted machine opens to a bridge that names the next quest, one click starts it, the map shows what is lit and what is fogged, a checkpoint lands as a card with a text box, and the crew roster shows which agent ran and what it cost.

Why this path
  • The bridge and the ship-systems room ship on data the server already parses or can parse with one loader each. The developer sees the game in two quests, before any map exists.
  • Staging the flight deck (L1, then L2, then L4) means every quest from quest 2 onwards is launched from the console, and the harness is the last thing built, not the first thing depended on.
  • The atlas is the only new data file. Its validator runs in the gate, so a tile that rots fails a merge instead of lying on a screen.
  • Every action stays inside ADR 0011's shape. quest-start, lesson-promote, and quest-run are rows in the same table, behind the same Host check.
Runner-up, and when it wins

E on M1 with L2 only. Stop after quest 5; the terminal stays the cockpit and the console never holds a session. It wins if the first quest-run shows a cost line the terminal does not, if exempting a job from the restart gate proves fragile, or if the developer finds the terminal's checkpoint prompt faster than a card. The console loses in-run visibility and the artifact-answer loop; it keeps everything else.

Confidence and what would change this

●●○. The SDK pieces — canUseTool, resume, the artifact watch on a main loop — are documented but have not run in this repo. Primary-source research

Sci-fi HUD grammar — what actually reads as a bridge

The BSG DRADIS is a distance-and-vector radar, not a mini-map

The reimagined series treats the DRADIS as a top-down and side-view stack showing bearing, range, and threat class — not the ship's location on a world map. That distinction matters if the console adopts the metaphor: a DRADIS-shaped panel names what is happening now, not where in the codebase we are. The map question (Q3) is independent of the sweep question.

Battlestar Wiki, DRADIS entry · en.battlestarwiki.org/wiki/DRADIS

Naturalistic sci-fi: no beeps, corners cut, wires visible

Ronald D. Moore's series bible for the reimagined BSG explicitly rejects the "clean" instrument aesthetic in favour of chunky handset phones, hull plating, and analogue-feeling readouts. The console's amber-on-hull look is faithful to this; a chrome or glassmorphic reskin would break the mood at the level of grammar, not palette.

Ronald D. Moore's "Naturalistic Science Fiction" bible for Battlestar Galactica, reproduced widely; primary URL uncertain — treat as secondary. A canonical excerpt is preserved at web.archive.org (Battlestar Galactica bible).

Ash Thorp on sci-fi HUDs: type, motion, and negative space carry the read

Working notes and talks from Ash Thorp (Prometheus, Ender's Game, Call of Duty title sequences) argue that the fictional HUD reads only when three things hold: monospace or engraved type in one weight, motion that is short and self-terminating, and generous negative space around the one instrument that matters. The CIC option (B) is a straight application of this.

Ash Thorp portfolio and talks · ashthorp.com

Kit Fui Ong / HUDs+GUIs — a working archive of fictional interfaces

HUDs+GUIs collects and dissects fictional-UI stills from film and games. Common patterns across the sample: labels sit outside the drawing (not on it); the accent is one hue against a near-monochrome ground; typographic scale is short (three sizes) not long. Every option here is compatible with that grammar; option A leaves the least room to break it.

HUDs and GUIs archive · hudsandguis.com

Info-density on game HUDs vs PM dashboards

Nielsen Norman: dashboards fail when they compete for the eye

NN/g's dashboard writing argues one focal signal per view, with supporting numbers arranged by proximity, not by symmetry. That is the case for the CIC landing (B) over an eight-panel bridge. A denser landing is not more informative; it is harder to scan.

Nielsen Norman Group, "Dashboards: Making Charts and Graphs Easier to Understand" · nngroup.com/articles/dashboards-preattentive

Tufte on dashboards: minimise chartjunk, maximise data-ink

Tufte's rule generalises: every mark that is not data pays rent. On the console, a scanline that is not tied to a state (running / idle / gate armed) is chartjunk. A scanline whose speed encodes the current job's progress is not.

Edward Tufte, "The Visual Display of Quantitative Information", 2nd ed. Cited from the author's site · edwardtufte.com/tufte/books_vdqi

Gamification — where it earns, where it backfires

Deterding et al. — gamification works when the game elements come from the domain

The 2011 CHI paper "From Game Design Elements to Gamefulness" argues that XP, points, and badges succeed when they encode signals the user already tracks. Verstaan already tracks quest-tier rarity, ADR count, gate stamps, and retro lines. XP built on those is honest; XP invented on top of them (arbitrary points per commit) reads as decoration and stops working within weeks.

Deterding, Dixon, Khaled, Nacke, MindTrek 2011 · dl.acm.org/doi/10.1145/2181037.2181040

The map — derived vs authored layout

Force-directed graphs of a codebase are legible for orientation, not for place

d3-force lays out nodes by simulated repulsion and link tension; positions are not stable between runs and carry no meaning of their own. A dev returning after two weeks cannot say "the engine region is top-left" because it may not be. That rules a pure force layout out as the map and leaves it fit for a zoomed-in region view where nodes are few and labels are read, not remembered.

d3-force reference, Mike Bostock · d3js.org/d3-force

Pan and zoom is a solved transform; the cost is in what you draw, not how you move it

d3-zoom applies one affine transform (translate + scale) to a container and emits it on wheel, drag and pinch; it works the same on SVG groups and on a Canvas 2D context. MDN's canvas guidance adds the rule that matters for a fogged map: pre-render static layers (terrain, fog) to an offscreen canvas and composite only the moving layer per frame. A few hundred tiles in SVG is fine; a few thousand wants Canvas.

d3-zoom · d3js.org/d3-zoom · MDN, Optimizing canvas · developer.mozilla.org/…/Optimizing_canvas

The launch and the channel

Claude Code runs headless with -p and takes a model flag; an interactive session needs a terminal

The CLI reference documents claude -p "<prompt>" for non-interactive runs (output to stdout, exit when done) and --model for the model per invocation. Slash commands such as /factory-run 21 are accepted as the prompt in either mode. What -p does not give is a human at a checkpoint: a prompt that waits for the user in an interactive session has no one to wait for in print mode. That is the whole difference between L2 and L3.

Claude Code CLI reference · code.claude.com/docs/en/cli-reference

A JSON POST to localhost is a "simple request": the browser never preflights it

Per the Fetch standard, a POST with Content-Type: application/json is not CORS-safelisted, but a cross-origin page can still send it as a no-cors request without a preflight; the response is opaque, but the server has already acted. ADR 0011 handles this today by refusing any POST whose Host header is not the console's own loopback address and port. Every new job kind — quest-start, lesson-promote — inherits that check for free by living in kinds.ts. A kind added anywhere else does not.

Fetch Standard, CORS-safelisted method and header · fetch.spec.whatwg.org/#cors-safelisted-method · Verstaan ADR 0011 · docs/adr/0011-console-actions-run-only-allow-listed-scripts.md

Print mode does not define what happens at a question; the SDK does

The headless page says AskUserQuestion and permission prompts are "handled in-loop" and stops there; with --permission-prompts none the ask tool is removed and any call to it is denied. The Agent SDK's canUseTool option receives (toolName, input) for every tool call, including AskUserQuestion, and returns { behavior: "allow", updatedInput } — which is where a host program supplies the developer's answer. query({ resume: sessionId }) continues a run by id; a streaming prompt of SDKUserMessages sends new input mid-run.

Headless mode · code.claude.com/docs/en/headless · SDK user input · code.claude.com/docs/en/agent-sdk/user-input · SDK sessions · code.claude.com/docs/en/agent-sdk/sessions · streaming vs single · code.claude.com/docs/en/agent-sdk/streaming-vs-single-mode

An artifact comment wakes only an interactive or SDK main-loop session

The artifacts page states it: a comment sent to Claude reaches the publishing session right away, and only an interactive or SDK main-loop session holds that watch — not a subagent, teammate, background, or print session. L2 and L4 qualify; L3 never did.

Claude Code artifacts, "Let Claude reply to comments on its own" · code.claude.com/docs/en/artifacts

A published page can keep a selection and take a comment without any new protocol

The artifacts docs describe two things the Q15 scene needs: a runtime db capability that lets a page store what viewers change, shared across viewers and readable back by the session with read_db; and comment threads a viewer sends to Claude, which reach the publishing session while it is interactive or an SDK main loop. A pros-and-cons page with one radio group per decision, plus a comment box, is the whole feedback surface. The /design canvas is the drawn-layout case of the same mechanism.

Claude Code artifacts · code.claude.com/docs/en/artifacts

A blocking MCP tool is allowed, but the main loop backgrounds it after two minutes

An MCP tool may block for as long as it likes; the limits are a per-server timeout in .mcp.json, MCP_TOOL_TIMEOUT, and an idle timeout (CLAUDE_CODE_MCP_TOOL_IDLE_TIMEOUT, 30 min on stdio). The catch for a checkpoint: a main-conversation call is moved to the background after 2 minutes (CLAUDE_CODE_MCP_AUTO_BACKGROUND_MS), so the model continues without the answer. That is why the checkpoint belongs in canUseTool, which blocks by design, and not in a blocking MCP tool.

MCP servers · code.claude.com/docs/en/mcp-servers

MCP is the documented way to hand a running Claude session a tool the console owns

The Model Context Protocol lets a local server expose tools and resources over stdio or HTTP; Claude Code loads them from .mcp.json, which this repo already uses for Playwright. A console MCP server with one tool — await_orders(checkpoint) that blocks until the developer answers on the artifact page — is the live channel Q13 names. It needs no polling and no shared file, and it is the only shape in which L3's checkpoints can live in the console.

Model Context Protocol specification · modelcontextprotocol.io/specification/latest · Claude Code MCP docs · code.claude.com/docs/en/mcp

Reduced motion is a media query the boot sequence must read

@media (prefers-reduced-motion: reduce) reports the OS setting. The one orchestrated launch moment from Q5 plays in full when the query is false and collapses to a fade when it is true. This is a CSS rule, not a toggle the console invents.

MDN, prefers-reduced-motion · developer.mozilla.org/…/prefers-reduced-motion

The console's own record

The mirror already puts one GitHub milestone per region and one issue per file

tools/factory/mirror_github.py writes one GitHub milestone per distinct milestone: value, one issue per file, and labels milestone:<m> and checkpoint:<n>; the issue's front matter records the result in github_issue:. The flow is one way, local to remote. Reading GitHub back for issue state returns what the files already say. Reading it for pull requests and check runs returns what the files cannot say: GET /repos/{owner}/{repo}/commits/{ref}/check-runs gives gate.yml's verdict per commit; the authenticated REST limit is 5 000 requests per hour, unauthenticated 60.
