Test Data for the Engine Gate

The premise holds in two places today and in four issue files tomorrow. The CI gate stopped importing the archive on 2026-09-15 and reads a store only on a branch that changed it, but it then reads that store on all three legs, and the local gate script still runs the full sweep that the same day's decision removed. Ahead of that, the M3 issue files send the engine's own GoogleTests to data/languages/eng, a 175 MB store of 574,846 entries, and the gate table plans to build every tier from that store at M4. Carve a fixture store per real language from the fifteen fixed sentences, point issues 19, 20, 22 and 23 at it, and let the whole store be read once, on one leg, only when a branch changes data or the tools that read it.

The decision

Which data the engine's tests, the fixture data library and the gate's tier builds read

The owner asked why the gates test and build with the real dictionary and grammar data, and what the better alternatives are. The question has two halves, and they have different answers.

The first half is the gate as it runs now. On 2026-09-15 the owner asked the same question about the importer tests, and the "Gate Time Budget" brief of that day answered it: the pytest step imported the 6 MB English zips and took ten to fourteen minutes, so the owner chose fixture-sized imports, issue 166. The same afternoon issue 168 stopped the validator sweeping both stores on every branch. Today the CI gate reads a real store in one place, tools.validate --changed --base, and only when the branch changed a file inside that store. A docs, engine or console branch reads no store at all. Two leftovers remain, and the research section measures them: the step runs on all three legs, and the local gate_full.sh still calls --all.

The second half is what comes next. The M3 issue files, written at the M2 close-out, name the real store as the test input for the engine. Issue 20 says engine/src/dictionary_lookup.cpp reads data/languages/eng/dictionary/*.yaml and its GoogleTest looks up every token of the fifteen sentences there. Issue 22 says the rule interpreter reads the five English and two Afrikaans grammar files from the store. Issue 23 picks its missing word against the real English dictionary. And SPEC.md §5 lists "all tiers configure and build" and step 6 "regenerate and diff" in the full gate, which at M4 means running the compiler over the whole store and compiling its output on every pull request. This brief decides the rule for that half before the first of those issues runs.

Assumptions
  • M3 keeps its scope: English → UNL → Afrikaans for the fifteen ugoa1 sentences issue 24 selects. The 248-sentence corpus is an M4 equivalence subject.
  • The runtime-tables back end of ADR 0007 needs a YAML reader somewhere. The engine has none today: vcpkg.json lists only gtest, and engine/CLAUDE.md forbids I/O under src/. Where that reader lives is an M3 design call this brief does not make; the data question is the same wherever it lands.
  • The owner's 2026-09-15 decision stands: validate --all runs by hand during data work, never on a timer. Nothing below adds a scheduled run.
  • Free public-repository runners, four vCPU and 16 GB, three build legs, a fifteen-minute build cap.

What the research says

The gate is clean today; the M3 files reopen the cost the owner just closed

Why the real data is there at all

Four reasons put the real store into the plan, and only one of them is still a reason to read it per pull request. First, the standard forbids inventing expected values: "the golden text for a sentence comes from the owner or from the archive corpus, never from the engine" (docs/standards/testing.md). Second, the M3 milestone is defined as real English into real Afrikaans, so the issue files reached for the real files as the shortest path to "real". Third, a branch that edits a store must answer for the whole store, which is why --changed validates every file beside the touched one (issue 168). Fourth, ADR 0006 says every tier build produces its own golden set "from the same corpus", which reads as the full corpus at M4.

The first reason is satisfied by a slice as well as by the whole, as long as the slice holds real lines verbatim with a manifest naming their source. That is exactly the shape issue 166 built for the archive zips. The second reason is a milestone claim, proven once at close-out, not a property of every fast-gate run. The third reason is right and stays. The fourth is a compiler contract and can be met from a fixture store too.

Two places still read the whole store today

The local full gate is the first. tools/factory/hooks/gate_full.sh line 80 runs python -m tools.validate --all and fails the gate when it exits non-zero. .claude/commands/gate.md, SPEC.md §5 and testing.md all say --all is never a gate step, since issue 168. The script did not follow. On this machine that line costs 352 seconds and exits 1, because the real stores still carry the feature-value errors quest 169 is clearing. So every local /gate run reads 185 MB of YAML for six minutes and then reports a failure the owner has already decided not to block on.

The CI build matrix is the second. Picture this morning's run on the importer branch, side quest 169, at 06:45 UTC. The branch touches the English store, so --changed correctly validates the whole of it. It does so on the clang leg for 3 min 29 s, on the gcc leg for 4 min 47 s, and on the MSVC leg for 3 min 58 s, in parallel, reading the same OS-independent YAML three times to learn one fact. The C++ build and ctest on each leg took under a minute. The 2026-09-15 brief named this: "the data is OS-independent … running them on Windows, gcc and clang three times proves nothing the Linux run does not".

Neither leftover needs a decision. The first is a one-line drift from a rule already written. The second is the data job described below, which the earlier brief held back until the store checks outgrew the build legs; a data branch now spends more time in the validator than in everything else together.

The store's shape, for a fixture

The homograph shape matters for a fixture. English bank carries 36 entries in b.yaml, and the single letter A carries 12 in a.yaml. A slice that keeps every entry for a chosen headword keeps the real fan-out; the lookup test in issue 20 sees the same 36 candidates it would see in the whole store.

What the M3 files cost if they run as written

This is the point in the flow where the cost arrives. Issue 20's test process opens the English shards, parses them and builds lookup structures before its first assertion. The fastest C++ YAML parser in common use, rapidyaml, reports about 150 MB/s on Linux and about 100 MB/s on Windows, so the parse alone is one to two seconds per process and the tree it builds for 4.6 million lines sits at several hundred megabytes (rapidyaml, "Is it rapid?"). yaml-cpp, the parser most C++ projects reach for first, is reported at ten to seventy times slower on the same benchmarks, which puts the parse at twenty seconds to two minutes (rapidyaml README). The Python validator with libyaml's C loader takes five minutes for the same store, and that is the only measured "read the English store" figure the project has today.

The multiplier is CTest. Issue 26 asks for gtest_discover_tests so that ctest -R A09 runs one row. That module registers "a separate CTest test for each Google Test test case" and runs the executable once per case (CMake, GoogleTest module). Every case then loads the store again. Fifteen golden rows plus the lookup, interpreter and status tests make forty or more processes, each paying the parse and the memory. On the owner's laptop ctest -j8 would hold eight copies of the store in memory at once. The Stop hook runs the fast label at every session stop, so this cost lands on every encounter, not only on the pull request.

Google's test-size rules name the line being crossed. A small test "must run in a single process", has no file-system access and is capped at sixty seconds; a test that reads files is at least medium, capped at five minutes, and is not what a pre-commit gate is built from (Google Testing Blog, Test Sizes). The project's own standard says the same in one line: "domain tests are pure: no file I/O … fixture data lives in tests/fixtures/" (docs/standards/testing.md). ADR 0003 promised that "the engine builds and its tests run against a tiny fixture data library, so engine work does not wait on the compiler". Issues 19, 20, 22 and 23 drift from all three.

Dissent. The issue files are not wrong about what M3 must prove. Fifteen real English sentences through real dictionaries and real rules is the milestone. The disagreement is about where that proof runs: once, when the store or the engine changes, or on every fast gate and every pull request.

What M4 adds if the gate keeps the whole store

The compiler emits engine/generated/<tier>/tables.cpp and the gate builds every tier (SPEC.md §3.5, §5). The phone and connected tiers carry the full dictionary, so their tables hold 574,846 entries as a C++ initializer. Large table initializers are a known compile-time hazard. Unity measured one descriptor table at 92 seconds for a single file in Release, cut to 10 seconds by moving the table to global scope and dropping the enum operators (Aras Pranckevičius, Slow to Compile Table Initializers). Clang has taken over ten seconds on a 40-million-element array that GCC compiled in under a tenth of a second (cor3ntin, Very Large Arrays in Clang), and MSVC has a filed case of compile time growing with the square of a large static initializer (Visual Studio Developer Community). Three compilers, three legs, one fifteen-minute cap. Step 6's regenerate-and-diff adds a Python pass over the 175 MB store per pull request, which the validator's five minutes already prices. And ADR 0003 commits the generated output, so every data change lands a tens-of-megabytes diff in git.

None of that is decided yet; the M4 quests do not exist. It is listed here because the rule this brief sets should carry to M4 without a third investigation.

How other rule-based translators split it

Apertium, the largest open rule-based machine translation project, keeps two kinds of test. Regression tests translate a small fixed set of phrases and compare against expected output; they are "deterministic, in the sense that they either pass or fail". Corpus tests translate a whole corpus and diff against the last run, "very useful if you want to change a rule or word and want to get an overview of the consequences on real-life text" (Apertium wiki, Corpus test; Apertium-regtest). The small set is the gate; the corpus run is the data tool. Verstaan already has both halves named: the golden label and the held-out slice for the first, the equivalence label and validate --all for the second.

What the platform offers for the real-store proof

A workflow can run only when named paths change: with on.pull_request.paths, "if any path names do not match patterns in paths-ignore … the workflow will run", and the filters apply to push and pull request events (GitHub Docs, workflow syntax). The aggregator job already treats a skipped cla job as a pass, so a path-filtered data job fits the existing shape. workflow_dispatch gives the same job a button for an on-demand run without a schedule (GitHub Docs, triggering a workflow). Public-repository runners are free and the job cap is a repository choice up to 360 minutes (GitHub Docs, Actions limits), so a twenty-minute data job costs nothing but wall time on the branches that need it. The 2026-09-15 brief listed this as "Skip data when data is untouched" and called it a refinement for later; M3 is when it is needed.

The alternatives

Five ways to feed the engine's tests, one of which the standard already asks for

Carved store fixtures

M

Cut a fixture store per real language, tests/fixtures/languages/eng/ and afr/, in the same §3.3 layout as the real one. It holds every dictionary entry, every sense, for every token of the fifteen sentences, the rules issues 21 and 22 name, the whole tagset, one heavy headword such as bank, and one word deliberately absent. A small carve tool under tools/ reads the sentence table and the real store and writes the slice, so the fixture is regenerated, not hand-kept, and a manifest line names the source shard and line of every entry.

Pros
  • Every engine test loads a store of a few hundred entries in milliseconds, on every leg and at every Stop hook.
  • Expected values and entries are still archive bytes, verbatim, so the golden rule in testing.md holds.
  • The compiler at M4 runs over the same fixture store, which gives the fixture data library and the equivalence test a real, cheap subject.
Cons
  • The whole-store run moves out of the pull-request gate; a data job or an owner-run step carries it.
  • Four issue files change their input paths before they run, and the carve tool is a small new quest.
  • A defect that only the whole store shows, such as a shard that no longer parses, is caught by the data job, not by an engine branch.
Fit here

Issue 24 already writes tests/fixtures/languages/eng/tests/basic.yaml, so the folder and the shape exist. Issue 166 already built the manifest pattern for carved archive zips. This is the same move one layer up.

Afterwards

ctest -L fast and -L golden finish in seconds. tests/fixtures/archive/manifest.jsonl gains sibling lines for the store slice. A pull request that touches data/languages/ shows one more check, data, and every other pull request shows it skipped, in grey.

★ Recommended

Stay as is

S

Run issues 19 to 25 as written. The engine's tests open data/languages/eng and afr directly, and the M4 gate builds every tier from the whole store.

Pros
  • Nothing to carve and nothing to regenerate; the test reads what ships.
  • The milestone's claim and the test's input are the same files.
Cons
  • Each test process parses 175 MB before its first assertion, and CTest runs one process per case.
  • Breaks three written rules: no file I/O in domain tests, fixtures under tests/fixtures/, and ADR 0003's tiny fixture library.
  • The cost scales with the store: Dutch at M6 and the 248-sentence corpus at M4 grow it again, the way the importer step grew until the cap cancelled it.
Fit here

This is the shape the owner rejected on 2026-09-15 for the importer, now at the engine layer, and with a C++ parser the project has not chosen yet.

Afterwards

The Stop hook's fast gate takes minutes. --output-on-failure logs open with a load time. The build job's cap is back in play at M4.

Fast loader, once per binary

M

Keep the real store as the test input but make the read cheap. Add rapidyaml to vcpkg.json, load the store once per test executable through a GoogleTest Environment, and register one CTest case per binary instead of per test case.

Pros
  • The parse drops to one to two seconds per binary on Linux; the whole store is exercised on every run.
  • No fixture to carve; the homograph fan-out and the shard layout are the real ones.
Cons
  • A new engine dependency, and a YAML reader the "no I/O under src/" rule has to house somewhere.
  • Several hundred megabytes per process, slower on MSVC Debug, and ctest -R A09 no longer runs one row.
  • Still reads the store three times per pull request and at every Stop hook, and still grows with every language added.
Fit here

The right tool for the data job's whole-store runs, and a reasonable choice for the runtime-tables reader itself. Not a reason to put the whole store in the fast gate.

Afterwards

A ryml port in vcpkg.json, one LoadStore line at the top of each test log, and a fast gate that takes ten seconds on a good day.

Real store in a data job only

M

Label every test that reads data/languages/ as store. The three build legs run everything else against xxa and xxb. A fourth job on ubuntu-latest, triggered by a path filter on data/** and the tooling packages, runs the store label, validate --lang for the touched stores, and the M4 regenerate-and-diff.

Pros
  • The real store is read once per run, on the fastest runner, and only when something that can change its meaning changed.
  • No fixture for real languages to maintain.
Cons
  • The fifteen-sentence golden tests are the engine's own regression suite, and an engine branch would never run them.
  • The invented pair cannot express an English homograph or an Afrikaans inflection paradigm, so M3's behaviour has no fast test at all.
  • A new reader of the store outside the filtered paths goes unchecked.
Fit here

The job is the right home for the whole-store proofs. On its own it leaves the M3 slice without a fast regression test, which is the wrong trade.

Afterwards

A grey "skipped" data check on most pull requests, and a green fast gate that proves nothing about English.

Cached compiled snapshot

L

Pull the M4 compiler forward: turn the store into a compact binary or the generated tables once, cache the result with actions/cache keyed on hashFiles('data/languages/**'), and let every test process load that in milliseconds.

Pros
  • Real coverage per pull request with a fast load, once the cache is warm.
  • The same artefact serves the tier builds later.
Cons
  • A cache miss, on every data change and on every fresh branch, pays the full five-minute-plus regeneration inside the build job.
  • The local gate and the Stop hook have no cache; the owner's machine pays every time.
  • It is M4's compiler built before the M3 interpreter it must reproduce, which inverts ADR 0007's order.
Fit here

A shape to revisit at M4 for the tier builds themselves. Not an M3 answer.

Afterwards

A "Cache restored from key" line in the job log on most runs, and a slow run whenever it says "Cache not found".

Recommendation

Carve the store the fifteen sentences need, and let only data branches read the whole one

Three reasons carry it. Every assertion in issues 19 to 25 is about a token, an entry, a rule or a row, not about the size of the store, so a slice that holds those entries verbatim proves the same things. It is what the standard, ADR 0003 and the owner's 2026-09-15 decision already ask for, applied one layer up from the importer. And it stops the growth: the engine's suite stops scaling with the archive, so Dutch at M6 and the full corpus at M4 do not put the fifteen-minute cap back in play.

Two small repairs come first and need no new decision. Replace --all with --changed --base origin/main at gate_full.sh line 80, so the local gate matches the three documents that describe it. And move the CI validate step out of the three-leg matrix into the data job below, so a data branch reads its store once.

The work, in outline, before /factory-run 24 and never on main:

# 0. Two repairs, one side quest
#    tools/factory/hooks/gate_full.sh:80   --all  ->  --changed --base origin/main   (issue 168's rule)
#    gate.yml: "Validate changed data" leaves the build matrix and joins the data job below

# 1. A side quest: the carve tool and the fixture store
python -m tools.fixture carve --lang eng --sentences tests/fixtures/languages/eng/tests/basic.yaml \
    --keep bank --absent <word issue 24 names>      # writes tests/fixtures/languages/eng/{dictionary,grammar,tagset.yaml}
python -m tools.fixture carve --lang afr --sentences ... # same for afr; every entry keeps its source shard and line
# tests/fixtures/archive/manifest.jsonl gains one line per carved file: store path, commit, line ranges

# 2. Four issue files change one phrase each
#    19, 20, 22, 23: "data/languages/<iso3>/..."  ->  "tests/fixtures/languages/<iso3>/..."
#    26: the golden loader reads tests/fixtures/languages/*/tests/*.yaml, as it already says

# 3. gate.yml: one job, `data`, needed by the aggregator, skipped-means-pass like `cla`
on: pull_request: paths: [data/languages/**, tools/importer/**, tools/validate/**, tools/compiler/**, tests/fixtures/**]
    workflow_dispatch:
jobs: data: runs-on: ubuntu-latest, timeout-minutes: 30
      - python -m tools.validate --changed --base ${{ github.event.pull_request.base.sha }}
      - python -m tools.fixture carve ... && git diff --exit-code tests/fixtures/languages/   # the slice is current
      - ctest -L store   # the real-store label, when M3 gives it content

# 4. SPEC.md §5 and testing.md, one line each
#    "The pull-request build legs read no file under data/languages/. Engine tests read tests/fixtures/.
#     Whole-store checks run in the data job, on branches that change data or the tools that read it."

The carve step's diff check is what keeps the slice honest. When a data branch changes an entry the fifteen sentences use, the fixture goes stale, the data job's diff fails, and the branch regenerates the slice in the same pull request. The slice and the store cannot drift apart without a red check.

The runner-up is the fast loader, once per binary. It wins if the owner decides that the milestone's proof must run on every pull request rather than on every data change. Then rapidyaml goes into the engine build, the store loads once per test executable, and the fixture slice is not needed. The price is a fast gate measured in seconds rather than milliseconds, a memory footprint of several hundred megabytes per process, and a suite that grows with every language.

Confidence is high. The store sizes and the validator's five minutes are measured. The C++ load figures are estimates from published parser throughput, because the project has not chosen a parser yet; a factor of two either way does not change the ranking.

What would change this

Four facts that would re-rank the options

  • The runtime tables are built by Python, not by a C++ reader. If the M3 design has the tooling emit runtime tables from the store and the engine loads a compact file, the parse cost moves to the tools and the engine tests read a small artefact. The carved slice still wins for the fast gate, but the fast loader option disappears and the cached snapshot becomes the M4 shape.
  • The owner wants the whole English store proven on every engine pull request. Then the fast loader is the answer for the golden label, and the data job carries only the validator and the regenerate-and-diff.
  • The M4 equivalence test must run all 248 corpus sentences through both back ends. The carve tool then takes the corpus as input instead of the fifteen-row table, and the slice grows to a few thousand entries. Still milliseconds.
  • A whole-store defect class appears that a slice cannot show. A shard that stops parsing, a tier that exceeds its memory budget, a homograph fan-out that only a rare headword has. Those are the data job's and tests/tier/'s business, measured on the real store, and they do not argue for reading it per test case.
